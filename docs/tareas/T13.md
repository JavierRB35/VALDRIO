## Real project cases

| Case | Model structure | Valid input and routing | Expected posted total |
|---|---|---|---|
| SERVICES | Two principals DELIVERY/CUSTOMER_SUCCESS; two auxiliaries ADMIN/IT | Six P&L accounts, a negative credit, a zero account, percent keys, 20%/10% self-service and bilateral auxiliary service, mixed/fixed/variable costs | EUR 17,500.00 |
| INDUSTRIAL | Three principals CUTTING/ASSEMBLY/FINISHING; two auxiliaries MAINTENANCE/ENERGY; lot/hour activity units | Seven P&L accounts, a supplier rebate, a zero account, percent keys, auxiliary cross-service and self-service, mixed/fixed/variable costs | EUR 36,000.00 |

Each project has `accounts.csv` (English descriptions, signed amounts with comma decimal separators) and `scenario.json` (centers, physical nodes, units, primary/secondary keys, classification, exact primary node amounts and independently derived terminal amounts). The sample data are wholly fictional.

`Synthetic Projects/verify_scenarios.py` verifies source codes, descriptions, distinct account IDs, 100% totals, primary reconciliation, mutual service matrix and eventual principal cost conservation using rational arithmetic. It does not invoke or certify the VALDRIO solver.

`T13SyntheticProjectsTests.cs` uses normal application services to create **actual SQLite company files**, publish models and keys, import accounts, classify resources, close primary, solve and close secondary, compare independently expected per-node amounts, freeze a snapshot and read it back from the file. It explicitly creates old-style keys whose saved self-allocation flag is Forbidden to verify the new unconditional self-service rule.

## Additional real-data regressions

`T13EdgeCaseIntegrationTests.cs` adds two extra end-to-end paths through the real application ports:

- **Direct / pool / excluded allocation:** a signed EUR 1,000 source split into EUR 300 directly attributable to a cost object, EUR 500 distributed through the primary and secondary pool, and EUR 200 explicitly excluded. The final terminal ledger must contain EUR 500 only; the resource reconciliation must still account for all EUR 1,000 without double counting.
- **Grouped closing balance with conflicting descriptions:** two source rows (EUR 280 + EUR 78.35) with the same account `6005` and different descriptions are grouped explicitly. Their names and provenance remain distinct, while the account is allocated once at EUR 358.35 and persists after reopening.

## Run locally on Windows

Prerequisites: Windows + .NET 10 SDK, local clone, clean branch and Python 3.

```powershell
git switch feature/t13-synthetic-projects-20261011
python "Synthetic Projects/verify_scenarios.py" --self-test
$env:VALDRIO_T13_EXPORT_DIR = Join-Path (Get-Location) "Synthetic Projects/Generated"
dotnet test tests/Valdrio.Tests/Valdrio.Tests.csproj -c Release --filter "FullyQualifiedName~T13_"
Remove-Item Env:VALDRIO_T13_EXPORT_DIR
pwsh -File .github/scripts/Verify-Windows.ps1
```

Generated and reopenable `.valdrio` files appear in `Synthetic Projects/Generated/Service Company/services.valdrio` and `Synthetic Projects/Generated/Industrial Company/industrial.valdrio`, alongside frozen study receipts. `Generated/` is excluded from source control to prevent accidental submission of binary test state. These files are only present **after successfully running the .NET tests on Windows**.

## Coverage limits and future extensions

This first pair covers successful imported P&L amounts, negative and zero lines, signed conservation, exact account-code routing, multiple principal/auxiliary nodes, mixed/fixed/variable cost, percent keys, self/allied auxiliary services, snapshot and reopening.

The two main reference company generators do **not yet** exercise every optional workflow. Extra T13 integration regressions now exercise grouping conflicting descriptions, direct objects and justified exclusions. Remaining gaps include FX and revaluation, balance-difference files, debit/credit column import, equal-share/driver-based keys, retries/cancellation/fault injection, duplicate import batches, archived version migrations and T12 persistence. These are existing tests in T02–T11, but must be brought into an expanded T13 acceptance matrix before claiming exhaustive product coverage.
